# Module 3.10: UI integration specification

Tracking: #997. This document specifies frontend work; no Blade/JavaScript changes are included in the backend migration.

## Server contract and ownership

Keep the existing Livewire public fields/actions and policy checks while replacing their implementation. Form fields remain UI state, not an ESOZ request document. The server loads a complete canonical resource through a repository, converts visible fields with fromFhir(), and uses the original resource as toFhir() context on save. Fields absent from the screen survive the round trip. Explicit removal must be represented as null or an empty list, not an omitted field.

SQL belongs to repositories. Payload serialization, remote status handling and full-resource fetch belong to Classes/eHealth. The UI does not infer remote registration from the existence of a UUID. Signature fields and key credentials must never enter the resource or migration report.

## Care Plan create and update

Components: CarePlanCreate, CarePlanUpdate, CarePlanForm, and CarePlanManager::signPlan.

- Preserve the current title/category/terms/encounter/author/description/note/inform fields. Requiredness for a local draft and for a remote create are separate server validations.
- Use the existing periodStartTime/periodEndTime fields together with the date fields. Display the effective timezone. A record loaded with seconds/fractions must retain them when its date/time was not edited.
- When user input is outside the encounter/plan bounds, show a field error. Do not move the date during signing or silently add a minute.
- Supporting information must support typed episode/procedure/diagnostic-report references as allowed by the endpoint. Removing episodes must not remove unrelated supporting information.
- Co-authors remain a list. A screen that displays one value must not replace the full saved collection on submit.

Acceptance: open a resource containing two supporting types, additional coding/text and a precise timestamp; edit only its title; reload and compare the preserved fields. The signed create content must be generated by the backend API contract, not independently assembled by the component.

## Activity create and update

Components: ManagesCarePlanActivities, CarePlanManager::signActivity, CarePlanActivityShow and the care-plan activity drawer.

- kind is service_request, medication_request or device_request. Do not derive the kind by substring matching a display label.
- Product selection stores its resource type with its UUID. Service and service_group must remain distinguishable. Device classification uses productCodeableConcept; selecting a reference clears that alternative and conversely.
- Quantity/daily amount/remaining quantity use separate value, system, code and unit fields. A translated unit label must not replace its code. Decimal values must not be converted to integers.
- Display zero remaining quantity as zero; absence means no reported quantity. Display remainingQuantityType alongside the value. The UI must not calculate an authoritative remote remainder.
- Preserve multiple reason codes/references and goals. Goals are CodeableConcept values, not UUID identifiers. Resource references retain their type.
- Scheduled period, timing and string are mutually exclusive modes. Until all modes have a UI, a stored unsupported mode must be retained and labelled as such, never replaced with today's default period.
- Keep doNotPerform=false in server state and request serialization.

Acceptance: medication activity with 1.2345 quantity; service-group product; device classification product; two goals and two authors; zero remainder; timing-mode resource edited only in description. Reload and sign without loss of any unedited field.

## Registry, details and synchronization

Components: CarePlanIndex, PatientCarePlans, CarePlanShow and CarePlanActivityShow.

- Date filters must use the canonical period through repository queries, not historical date-only columns.
- Synchronization state is distinct from clinical status. A pending remote job must not appear as successfully accepted.
- Summary records do not replace detailed resource state. Preserve the displayed record if full import fails, report the failure through the established session flash pattern and permit retry.
- Unknown external authors retain their reference. Do not display the local plan author as a substitute for an activity author.
- A backend list/detail adapter must provide the current template's expected fields without relying on lazy SQL from model accessors.

Acceptance: paginate a sync, repeat it, then fail one detail fetch. Previously loaded full fields remain intact, retries do not duplicate entries and no success message is shown for the failed operation.

## Complete and cancel

Components: CarePlanManager completion/cancellation actions and related dialogs.

- Completion obtains reason/outcome concepts from the appropriate dictionaries and submits the dedicated unsigned action body.
- Cancellation fetches the authoritative remote snapshot. Missing access, 404 or connection failure blocks signing; do not fall back to a local create payload.
- The payload preview/signing source is immutable during signature collection. Show a recoverable error on submission failure; do not rebuild a different payload and reuse the old signature.
- The current KEP modal remains the signing interface. Real signing is performed by the user.

Acceptance: compare the remote snapshot and unsigned cancellation content, allowing only the endpoint's documented modifications. Completion must not send unrelated snapshot fields. Failed or pending operations do not change the clinical state to a successful result.

## Linked workflows and exclusions

Care-plan prescription/referral drawers consume the same canonical activity references and quantity data through backend adapters. Their own request payloads and lifecycle are migrated under modules 3.9 and 3.17. Standalone DeviceRequest from Encounter is maintained in its separate PR and must not be rewritten here.

## Cutover gates

Mandatory: existing fields/actions remain compatible; unsupported collections and schedule modes are preserved; no timestamp/quantity loss; registry adapters avoid stale historical columns; error and pending state are represented truthfully.

Deferred visual work: richer selectors for multiple concepts/references, explicit schedule-mode controls, external-author details and remaining-quantity labels. If a current form cannot safely preserve an unsupported value, disable editing that part until its UI is implemented; do not discard it to keep a save button enabled.

Record acceptance against the relevant 3.10 requirement and backend regression test. This specification does not certify completion of the entire module's ESOZ business requirements.
