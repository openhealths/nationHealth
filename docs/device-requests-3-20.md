# Е-запити на медичні вироби: реалізація та перевірка ТВ 3.20

Дата: 10.10.2026. Issue: [#963](https://github.com/openhealths/nationHealth/issues/963). Гілка: `Mefizz/ohealth:i963_device_requests_3_20`. База: `openhealths/nationHealth:main`.

Функціонал реалізовано для чотирьох розділів 3.20: створення, підписання, перегляд/управління та використання призначення плану лікування. Автоматичні перевірки працюють із підставленими відповідями API та ізольованою БД. Вони не підтверджують проходження приймального тестування ЕСОЗ: реальні КЕП, СМС, відпуск виробу та друк потрібно перевірити на тестовому середовищі.

## Що було в main і що змінено

У main вже були плани лікування, призначення виду `device_request`, SQL-облік запитів, мапер та частина API. Однак окремі екрани не утворювали повного процесу 3.20: не було повної перевірки актуальних конфігурацій і параметрів виробу, обмежень кількості, відновлюваної перевіреної чернетки, усіх дій над запитом та друку з обов’язковими даними. Сторінка відпусків містила демонстраційні записи.

Новий процес використовує існуючий `DeviceRequestLifecycleService`, SQL-моделі, `SignatureService`, резолвер асинхронних запитів та компоненти повідомлень. Додаткові залежності не встановлювалися.

Точки входу:

- Перегляд інкаунтера: блок «Е-запити на виріб» і кнопка «Додати Е-запит» за наданим зображенням. Перед переходом перевіряються пацієнт, права, автор і дата взаємодії.
- Призначення медичного виробу в плані лікування: перехід до форми зі збереженими ідентифікаторами плану й призначення.
- Картка пацієнта: посилання на реєстр е-запитів; старі дії над виробами переводять до нового процесу.
- Реєстр без контексту пацієнта: спочатку вибір пацієнта, потім пошук його запитів.

Повний Figma-макет за наданим URL не вдалося відкрити. Візуальна відповідність усього процесу Figma ще потребує перевірки; доданий блок інкаунтера спирається на зображення користувача та існуючі стилі застосунку.

## Відповідність пунктам ТВ

### 3.20.1 — початковий контекст і права

- **3.20.1.1.1:** використовується ідентифікований пацієнт із картки/реєстру; API викликається в його контексті.
- **3.20.1.1.2:** вибір завершеної взаємодії поточного працівника за сьогодні. Автор, пацієнт і `encounter.period.end` повторно перевіряються на сервері перед виписуванням.
- **3.20.1.1.3:** ідентифікатори плану й призначення зберігаються в захищеному стані компонента, чернетці та підписаному запиті. Їх не можна замінити полями браузера під час підписання.
- **3.20.1.1.4:** отримуються активні програми типу `DEVICE`; налаштування обраної програми читаються через `Get Medical Program by id`.
- **3.20.1.1.5:** виріб, віднесений актуальною конфігурацією до ДЗР, не допускається до виписування за програмою.
- **3.20.1.1.6:** застосовуються всі три API конфігурацій: довідників, виробів і параметрів. Переліки конфігурацій та каталогу читаються з усіх сторінок; неповні метадані пагінації блокують виписування.
- **3.20.1.2:** створення доступне активним `DOCTOR`/`SPECIALIST` із відповідним scope у поточному закладі.
- **3.20.1.3:** перегляд та дії доступні також `ASSISTANT`/`MED_ADMIN` відповідно до scope. Підтримується існуюча роль `MED_COORDINATOR`. Зайвий write scope асистента не дозволяє виписування і не заважає перегляду.

Перевірено автоматично: ролі, поточний permission team, власна/чужа взаємодія, сьогоднішня/вчорашня дата, пагінація та актуальні конфігурації. Повний сценарій кожної ролі з реальними токенами ЕСОЗ — ручний UAT.

### 3.20.2 — створення та підписання

- **3.20.2.1.1–3:** `intent=order`, поточний працівник у `requester` та поточний час у `authored_on` формуються сервером.
- **3.20.2.2.1.1–2:** вибір типу через dictionaries v2/конфігурації або пошук моделі через device definitions v2. Каталог враховує класифікацію й участь виробу в обраній програмі.
- **3.20.2.2.2, 3.20.2.2.2.1:** період вводиться у формі; його тривалість перевіряється за актуальним `request_max_period_day`. Для запиту з ПЛ період має вкладатися в періоди плану та призначення. Дата завершення не подовжується до кінця дня.
- **3.20.2.2.3.1.1:** одиниця кількості за програмою відповідає `packaging_unit`.
- **3.20.2.2.3.1.2:** кількість обирається з виключного переліку, утвореного об’єднанням кратних усіх доступних упаковок. Враховуються денна межа, фактична тривалість курсу й актуальний `remaining_quantity`. Якщо перелік довгий, доступне розширення наступними значеннями. Те саме обмеження перевіряється сервером.
- **3.20.2.2.3.2:** без програми кількість можна не вказувати; `null` зберігається й не перетворюється на 1. Якщо кількість зазначена для запиту з ПЛ, діє перевірка залишку.
- **3.20.2.2.4:** підтримується масив причин із посиланнями на condition, observation та diagnostic report.
- **3.20.2.2.5.1–3:** усі обов’язкові характеристики конфігурації включаються в запит. Є boolean, string, quantity, range та codeable concept, типи й словникові значення перевіряються. Дозволені значення для кількох кодів моделі перетинаються; порожній перетин блокує виписування. За відсутності обов’язкового переліку можна додавати необов’язкові характеристики з довідника. Остаточну перевірку властивостей моделі виконує API prequalify/Create.
- **3.20.2.3, 3.20.2.3.1–2:** вибір `inform_with`, OTP за замовчуванням і підтвердження актуального номера. При зміні номера підтвердження стає недійсним. Без підтвердження показується повідомлення ТВ з номером 1677. Після відновлення чернетки телефон потрібно підтвердити знову.
- **3.20.2.4:** форма редагується до створення; перевірена чернетка зберігається транзакційно й відновлюється. Перед КЕП дані повторно перевіряються за актуальною конфігурацією та залишком. Підписується серверний знімок чернетки, а не змінені після перевірки поля браузера.
- **3.20.2.5:** використовується реальний `SignatureService` та PKCS7-пакет `signed_data`; викликається Create Device request. Асинхронні prequalify/Create очікуються через job resolver. Успіх показується після читання створеного ресурсу зі статусом `active` і номером.
- **3.20.2.5.1:** при помилці підписання/створення ініціюється повторне отримання параметрів форми, включно з поточними налаштуваннями програми.
- **3.20.2.6.1–2, 3.20.2.7.1–2:** чотири повідомлення ТВ для комбінацій програма/без програми та OTP/THIRD_PERSON/документи/без методу. Тексти зберігаються в українських перекладах, результат показує існуючий компонент через Session::flash.
- **3.20.2.8.1–9, включно з 3.20.2.8.8.1–2:** друкована пам’ятка A5 містить requisition, CODE128A, тип/модель, кількість/одиницю, authored_on, occurrence_period, dispense_valid_to, заклад, лікаря, identity пацієнта, програму, funding_source та всі parameter. Для програми з документами/без методу потрібен код погашення з urgent; його відсутність блокує неповний друк. Funding source отримується за ID програми, зокрема для вже неактивної історичної програми.

Перевірено автоматично: контракт payload, повторна перевірка перед КЕП, захист чернетки від підміни, кількість/упаковки/залишок/періоди, характеристики, автентифікація, асинхронний prequalify, HTML A5 та CODE128. Реальний сертифікат КЕП, чотири повідомлення після запису в ЕСОЗ і фізичний друк — ручний UAT.

### 3.20.3 — реєстр, управління та відпуски

- **3.20.3.1.1:** пацієнт обов’язковий; фільтри закладу, статусу, коду виробу, епізоду, взаємодії та програми; пагінація.
- **3.20.3.1.2.1–10:** деталі показують статус, номер, тип/модель із довідниковою назвою й додатковими даними каталогу, кількість/одиницю, усі дати, reason, заклад, лікаря, subject, програму, status_reason та parameter.
- **3.20.3.1.3:** попередження про одноразовість СМС і підтвердження номера. Незалежний SQL-журнал із унікальним ID ресурсу захищає від повторної відправки, навіть якщо запит ще не синхронізований локально. Успіх повідомляється після завершення API/job.
- **3.20.3.1.4:** revoke лише активного запиту, причина з `device_request_revoke_reasons`, КЕП та повний актуальний ресурс для підписання.
- **3.20.3.1.5:** complete лише активного запиту без кількості; без КЕП.
- **3.20.3.1.6:** mark in error для будь-якого статусу, крім entered-in-error; словникова причина, обов’язкове пояснення й КЕП. Підписується повний ресурс.
- **3.20.3.1.7–8:** справжні списки та деталі device dispenses у картці пацієнта й у контексті е-запиту; фільтр `based_on`, пагінація. Демонстраційні записи прибрано.

Дії використовують PATCH-контракти patient API. Результат зміни статусу додатково підтверджується GET ресурсу. Сервер перевіряє права та заклад створення ресурсу незалежно від доступності кнопки.

Перевірено автоматично: методи/URL API, повний підписуваний ресурс, допустимі переходи, обов’язкове пояснення, одноразове СМС, зміна номера й невизначений результат після timeout. Усі реальні записи/СМС/відпуски — ручний UAT.

### 3.20.4 — план лікування та призначення

- **3.20.4.1:** використовується існуючий пошук ПЛ за requisition та іншими параметрами, з перевіркою доступу до плану.
- **3.20.4.1.1–10:** додано читання актуальних деталей ПЛ з ЕСОЗ: публічний номер, status, category з довідниковою назвою, title, period із необов’язковим end, encounter, supporting_info, addresses, description, status_reason та note. Оновлення доступне на сторінці й виконується після зміни стану плану. При помилці читання відображається повідомлення, що залишилися локальні дані.
- **3.20.4.2:** зберігається існуючий перелік і деталі призначень `device_request` у ПЛ.
- **3.20.4.3:** перехід до виписування повторно перевіряє активність і періоди плану/призначення за API.
- **3.20.4.4:** cancelled/completed призначення та terminated/cancelled/completed плани блокують виписування, навіть якщо локальна картка ще показує попередній стан.

Перевірено автоматично: всі заборонені комбінації статусів, періоди з необов’язковим кінцем, повні remote references/status_reason та екранування HTML. Пошук за реальним публічним номером і весь перелік призначень — ручний UAT.

## Автоматична перевірка

Середовище: Sail PHP 8.5.3, окремий контейнер застосунку та PostgreSQL з БД `testing` на tmpfs, без доступу до робочої БД. Міграції нового функціоналу застосовано. Існуючу міграцію завантаження ICD-10 із зовнішнього сервісу пропущено при підготовці ізольованої схеми.

Цільовий набір: **76 тестів, 208 assertions, без failures/errors**. Є попередження PHP 8.5 у незміненому `config/database.php:64`: `PDO::MYSQL_ATTR_SSL_CA` deprecated. Через це Laravel позначає успішні тести як deprecated.

Перевірені файли тестів:

- `tests/Feature/DeviceRequest/DeviceRequestComplianceTest.php`
- `tests/Feature/MedicationRequest/StandaloneRequestSigningTest.php`
- `tests/Unit/Services/MedicalEvents/DeviceRequestPrescribingTest.php`
- `tests/Unit/Services/MedicalEvents/DeviceRequestMapperTest.php`
- `tests/Unit/Services/MedicalEvents/EHealthJobResolverTest.php`
- `tests/Unit/Services/MedicalEvents/ReferralPrintoutCode128Test.php`
- `tests/Unit/CarePlan/CarePlanActivityValidationServiceTest.php`
- `tests/Unit/Services/MedicalEvents/ReferralSignPayloadTest.php`

Додаткові перевірки: Pint змінених файлів, PHP lint, компіляція Blade, маршрути та Vite build. Для збірки з readonly node_modules застосовано `npm run build -- --configLoader runner`.

Ширший старий `ReferralLifecycleTest` запускали, але він не проходить у цьому середовищі: посилається на відсутній уже в базовому main `DeviceActivityReadinessAssessment`, потребує налаштування Cipher та має розбіжність старого очікування local based_on ID. Це не зелений результат повного suite; такі перевірки не включені до наведеної кількості. У спільному `MedicationRequestForm` прибрано дубль атрибута Locked, який заважав наявним тестам підписання.

## Приймальне тестування перед закриттям ТВ

Потрібні тестовий заклад ЕСОЗ, активні працівники з відповідними ролями, ідентифікований пацієнт, його методи автентифікації, взаємодія лікаря за сьогодні, програма DEVICE, каталог, ПЛ/призначення та КЕП користувача. КЕП і пароль вводить користувач; автоматичний обхід модального вікна не застосовується.

1. Відкрити власний інкаунтер і перевірити нову кнопку; перевірити відмову для чужої/вчорашньої взаємодії.
2. Створити за програмою запит за типом і за моделлю, з різними упаковками, усіма видами параметрів і причинами. Перевірити межі періоду, денну кількість та залишок ПЛ.
3. Створити ДЗР без програми, у тому числі без quantity. Перевірити заборону ДЗР за програмою.
4. Перевірити OTP, THIRD_PERSON, документи та відсутність методу; непідтверджений/змінений номер; усі чотири повідомлення після реального створення.
5. Відновити й виправити чернетку. Змінити конфігурацію програми/залишок до КЕП, переконатися в повторній перевірці й оновленні налаштувань після помилки API.
6. Підписати справжнім КЕП та дочекатися Create/job/GET. Перевірити номер і активний статус.
7. Надрукувати A5 для програми й без програми, перевірити всі поля, CODE128A сканером, фінансування, identity та offline-код погашення. Перевірити кілька сторінок при багатьох характеристиках.
8. Перевірити всі фільтри реєстру, довідникові назви й деталі під кожною дозволеною роллю.
9. Повторити СМС один раз; перевірити заборону другого виклику, результат помилки й timeout без дублювання.
10. Виконати revoke з КЕП, complete без КЕП для запиту без quantity та mark in error з КЕП/поясненням. Перевірити реальні статуси й повідомлення.
11. Виконати тестовий відпуск та перевірити списки й деталі device dispenses.
12. Знайти ПЛ за requisition, перевірити всі десять груп полів і всі призначення, активні/прострочені періоди, плани без дати завершення та всі заборонені статуси.
13. Звірити повний frontend із Figma й підтвердити показ повідомлень у верхньому правому куті без дублювання.

До виконання цих кроків статус функціоналу — **реалізовано й перевірено автоматично, очікує приймального UAT/тестування ЕСОЗ**. Передумови інших модулів, перелічені перед 3.20 у ТВ, цією зміною не сертифікуються.

## Міграція та експлуатаційні особливості

Міграція `2026_10_09_171945_add_device_request_prescribing_data.php` є в install та update/0_1 з однаковим вмістом: nullable quantity, JSON-знімок чернетки, remote details та журнал повторного СМС. Слід застосувати її стандартним процесом оновлення середовища перед UAT.

Старі чернетки без знімка потрібно сформувати заново з призначення ПЛ. Rollback не повертає обов’язковість quantity, щоб не вигадувати клінічну кількість для записів без неї. Після невизначеного результату СМС журнал зберігає спробу й блокує повтор: результат необхідно з’ясувати, перш ніж дозволяти нову спробу. Тимчасові контейнери збережено для перевірки відкритого PR; робоче середовище не змінене.
