# План виправлень модуля планів лікування

Issue: [#1196](https://github.com/openhealths/nationHealth/issues/1196).
База аналізу: `main@3be59d5d48eb514b4d01abe30f1d52bd04d67381`, 11.11.2026.

**Статус: початковий план збережено як історію аудиту.** Реалізація входить у PR #1197;
актуальні результати, додаткові BA01/BA02/BA08 і межі перевірки наведено в
[`docs/tv39-remediation/care-plan.md`](tv39-remediation/care-plan.md).
Позначки нижче описують початкову матрицю, а не поточний статус виконання.
Ручне інтеграційне приймання залишається відкритим.

## Порядок реалізації

| Етап | Пріоритет | Залежність | Перевірюваний результат |
|---|---|---|---|
| 1а. Актуальний контракт | P1 | Немає | Записані правила для кожного зв’язку та середовища; приклади валідної/невалідної відповіді |
| 1б. Зв’язки і валідація | P1 | 1а | Обидва зв’язки проходять повний цикл чернетки, підписання та читання без втрати |
| 2. Кількості й періоди | P1 | Контракти відповідних kind | Значення відбираються/валідуються узгоджено у UI й перед підписанням |
| 3. Ролі та автор | P1 | Актуальні конфігурації ролей і правило Author/Encounter | Дозволений користувач може виконати дію; відмова не має побічних ефектів |
| 4. Пошук і перегляд | P2 | 1б для фільтрів/відображення зв’язків | Належний пошуковий результат доступний без неявної вимоги локальної картки |
| 5. Обмеження відміни | P1 | Буквальне правило ТВ 3.10.4.5.1 | Completed-призначення блокують відміну ПЛ |
| 6. Регресія й UAT | P1 | Реалізовані попередні етапи | Докази за критеріями приймання, включно з видимими помилками та pending |

Кожен кодовий етап виконувати окремим завершеним комітом із відповідними цільовими перевірками.
Починати зі зв’язків і валідатора; не об’єднувати їх із необов’язковим очищенням сусіднього коду.
Після оновлення базової гілки повторно перевіряти, які прогалини ще залишилися.

## Проблема

В актуальному `main` (`3be59d5d48eb514b4d01abe30f1d52bd04d67381`) сценарії «створений на основі іншого плану» (`based_on`) та «створений як частина іншого плану» (`part_of`) незавершені:

- обидва списки у формі містять лише порожній пункт;
- збереження/редагування чернетки не передає ці поля;
- mapper не перетворює вибраний UUID на Reference;
- `CarePlanForm::buildCreateContent()` вилучає обидва зв’язки перед підписанням;
- отримані з ЕСОЗ правильні Reference підтримуються сховищем, але не відображаються на сторінці плану;
- валідатор деталей CarePlan перевіряє лише id/status/title, тому не відхиляє пошкоджені зв’язки до persistence.

Окремо аудит ТВ 3.10 виявив прогалини кількостей, необов’язкового періоду, ролей/автора та пошукового результату. Це план усунення виявлених прогалин, а не підтвердження невідповідності всього модуля. Автотести та ручний UAT аудиту не виконувалися.

## План робіт

### 1. Контракти і зв’язки між планами — перший пріоритет

- [ ] Перед реалізацією звірити чинні API потрібного середовища: структуру, допустимі статуси та доступ для `based_on` і `part_of` окремо.
- [ ] Реалізувати пошук/вибір доступних ПЛ того самого пацієнта із зрозумілим номером, назвою і статусом; зберегти можливість не вибирати зв’язок.
- [ ] Узгодити camelCase form state, UUID ↔ одиничний Reference типу `care_plan`, створення/редагування/повторне відкриття чернетки та явне очищення значень.
- [ ] Зберегти обидва поля у підписуваному контенті для всіх шляхів створення, включно зі збереженою чернеткою.
- [ ] Показувати наявні зв’язки після створення/синхронізації; дозволяти відкриття пов’язаного ПЛ тільки з належним доступом.
- [ ] Валідовувати отриманий ресурс за офіційним контрактом до mapping/persistence/UI-рішень. Перевірити list/detail та делегування validator.
- [ ] Покрити правильні й пошкоджені Reference, чужого пацієнта, відсутні права, неприйнятний статус та збереження обох полів у payload.

`based_on` і `part_of` — різні зв’язки; їх наявність не запускає копіювання призначень або перенесення залишків. У ТВ 3.10.1.2.3 вони окремо не названі як обов’язкові поля; зв’язок із вимогами — загальна узгодженість зі специфікацією (3.10.1.2) та офіційний бізнес-процес.

### 2. Кількості та періоди призначень — ТВ 3.10.2

- [ ] Узгодити додатну цілу кількість послуг із ТВ 3.10.2.7.4; перевірити обов’язковість quantity/program окремо для кожного kind.
- [ ] Для виробів за програмою сформувати допустимий перелік кількостей: упаковки, кратність і верхня межа `max_daily_count × (end − start + 1)` (3.10.2.7.3); дублювати контроль на сервері.
- [ ] Урахувати допустимі варіанти упаковок ліків, а не лише першу.
- [ ] Дозволити нове призначення без програми й без періоду, коли це дозволяє API/ТВ (3.10.2.9.2); перевіряти частково введені/обернені дати та вихід за межі ПЛ.

### 3. Ролі, автор і права доступу

- [ ] Звірити MED_COORDINATOR із чинними конфігураціями author types/scopes і ТВ 3.10.1.1, 3.10.2.1; перевірити окрему роль без паралельного DOCTOR/SPECIALIST.
- [ ] Перевірити автора ПЛ проти автора/виконавця вибраної взаємодії та КЕП; відтворити кілька employee і взаємодію іншого лікаря (3.10.1.2.1). Вибір виправлення визначити після звірки контракту.
- [ ] Перевірити власника/заклад, чинний write approval та дозволені/заборонені дії. Відмова має відбутися до API/DB/queue side effects із перекладеним session flash.

### 4. Пошук і відображення — ТВ 3.10.3

- [ ] Відобразити належні дані пошукового результату за requisition, включно з `identity.short_name`/`identity.age`, відповідно до доступу.
- [ ] Перевірити пошук пацієнта без локального запису: не робити наявність локальної картки неявною передумовою показу доступного результату.
- [ ] Узгодити доступні пошукові параметри, зокрема `based_on`/`part_of`, із контрактом; локальні фільтри відрізняти від пошуку в ЕСОЗ.
- [ ] Зберегти вже реалізовану поведінку реєстру з #1172; не дублювати роботу #1185 щодо повідомлень синхронізації дозволів.

### 5. Обмеження відміни ПЛ

- [x] Застосувати буквальне правило 3.10.4.5.1: scheduled, in_progress і completed-призначення блокують відміну ПЛ.
- [x] Вилучити непідтверджене твердження про суперечність ТВ/API. Офіційний опис Cancel Care Plan (operation-0171, рядки 10–22) визначає рівність підписаного контенту, відсутність activities та status_reason; він не доводить дозвіл відміни за наявності completed-призначень.

### 6. Перевірка і завершення

- [ ] Мінімальні послідовні зміни без нових сервісних шарів та стороннього рефакторингу. Repository factories, imports/aliases і правила повідомлень — за `docs/CODE_STYLE.md`.
- [ ] Цільові тести mapper/payload/API validation/persistence/Livewire та негативні permission cases без побічних ефектів.
- [ ] Ізольоване тестове середовище; робочу БД не очищати, не мігрувати і не засівати для перевірок.
- [ ] Ручний UAT: вибір → чернетка → повторне відкриття → КЕП → pending/підтверджений результат → синхронізація → видимі зв’язки.
- [ ] Оновити матрицю пунктів ТВ лише за фактичними доказами; невиконані перевірки залишити відкритими.

## Критерії приймання

1. Обидва зв’язки працюють окремо і разом, зберігаються/очищуються у чернетці, входять у підписаний запит і відображаються після повторного читання.
2. Невалідні відповіді/посилання відхиляються до persistence; відмова через права не має побічних ефектів.
3. Для кожного виду призначення кількість і період відповідають узгодженим API/ТВ; помилки видно у відповідній формі.
4. Права ролей, автор та результати пошуку перевірені окремими позитивними й негативними сценаріями.
5. Відміна ПЛ дотримується буквальної заборони ТВ для completed-призначень; автоматизовані перевірки не замінюють ручне інтеграційне приймання issue.

## Додаткові умови реалізації

- Повторно перевіряти доступ до пов’язаного плану на сервері при збереженні та підписанні; значення public form state не є доказом доступу.
- Обробляти три стани редагування зв’язку явно: залишити наявне значення, установити нове, очистити. Null/порожній рядок не повинні випадково відновлювати старий Reference.
- Для передавання в API використовувати канонічний Reference; не плутати UUID плану з локальним id рядка Identifier.
- Для зовнішнього ПЛ без доступних деталей відображати лише дозволені контрактом дані. Перехід до деталей повторно перевіряє policy; відсутній локальний запис не означає дозвіл на імпорт.
- Не позначати pending успішно створеним ПЛ. Не повторювати create для тієї самої незавершеної операції; після confirmed result прочитати й відобразити збережені дані.
- КЕП і patient confirmation виконуються користувачем під час ручного UAT; signing-field errors залишають модальне вікно відкритим із видимими повідомленнями.
- Нові міграції планувати лише після перевірки наявного Identifier/FHIR storage. За поточним аудитом сховище правильних Reference вже існує; перевірити це тестом до рішення про схему.

## Мінімальна матриця регресії

| Група | Позитивні випадки | Негативні випадки / межі |
|---|---|---|
| Зв’язки | Немає зв’язків; лише based_on; лише part_of; обидва; save/reopen/edit/clear | Чужий пацієнт, відсутній доступ, відсутній план, неприйнятний статус згідно контракту кожного поля |
| Payload та sync | Canonical Reference у кожному create path; однакові значення після sync | Scalar замість Reference, неправильний ресурс, пошкоджений identifier; відмова до persistence |
| Кількість | Допустимі значення для кожного kind; різні упаковки; граничний максимум | Нуль, від’ємне, дробове service/device, пропуск обов’язкового поля, некратна упаковка, понад максимум |
| Період | Без програми й без періоду; коректний період у межах ПЛ | Програма без обов’язкових дат, одна дата, обернений період, вихід за межі ПЛ |
| Автор/доступ | Кожна дозволена роль, чинний write approval, коректний employee/signature | Окремий MED_COORDINATOR до/після узгодженого виправлення, кілька employee, чужий заклад, відсутній/нечинний approval |
| Пошук/UI | Requisition, належні identity-поля, зв’язки, локальний і відсутній локально пацієнт | Немає результатів, 403, пошкоджена відповідь, помилка наступної сторінки, відсутні права |
| Асинхронність | Pending → confirmed, відновлення після відкриття сторінки | Failed, повторне натискання під час pending, помилки КЕП і доступу без побічних ефектів |

Виконання матриці документувати фактичними командами/результатами та ручними сценаріями.
Тести, що лише повторюють структуру реалізації, не замінюють перевірку втрати зв’язків і відмов без побічних ефектів.
